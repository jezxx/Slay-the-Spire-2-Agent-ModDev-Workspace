# 从塔1移植到塔2的语义陷阱

移植不是逐字翻译。塔1 的命名、列表方向、Action 语义和塔2 的模型/命令语义经常不一一对应。每个映射都要有“塔1行为、塔2入口、实机验证”三列。

## 常见错位

- 塔1 的 addToTop 等命名不一定等于塔2 的列表开头；应按实际牌堆顺序和 UI 结果验证。
- “从弃牌堆取牌”可能是玩家选择、随机选择或按条件搜索，必须阅读对应实现，不能只看方法名。
- 塔1 的 DamageType.NORMAL、NORMAL 攻击和塔2 的 ValueProp/PoweredAttack 不是字面等价；先建立映射。
- 塔1 的 limbo、播放历史、状态层数和能力继承方式不能直接照搬；寻找塔2 的实际状态和生命周期。
- 塔1 的“每层一个类”不一定适合塔2；若塔2 用一个模型的 Amount 表示层数，应使用塔2 的模型结构。
- X 费卡需要同时满足 UI 成本和运行时执行契约，漏掉对应 override 可能导致卡面和效果一起失效。
- 敏捷、力量、脆弱、虚弱等名称要以塔2 当前的伤害/格挡管线为准，不要把塔1 的语义假设带过来。

## 迁移步骤

1. 从塔1源码或反编译结果提取“用户能观察到的行为”，而不是先复制类结构。
2. 在塔2 API/反编译资料中寻找最接近的命令、钩子、模型和资源路径。
3. 对列表顺序、随机性、时序、目标合法性、升级和本地化单独写断言。
4. 用最小卡牌/遗物/能力复现，再接回完整项目。
5. 记录仍然无法等价的部分，交给用户拍板，不要默默替换为看似相近的行为。
