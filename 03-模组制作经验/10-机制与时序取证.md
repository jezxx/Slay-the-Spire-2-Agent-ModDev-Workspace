# 机制、API 与时序取证

塔2 模组最容易出错的地方不是不会写 C#，而是把名称相似的入口、状态和时序想当然地对应起来。遇到机制问题时，优先读取当前版本程序集、调用点和运行日志。

## 先分清三类扩展方式

1. 原生继承/生命周期钩子：模型或能力本身提供 virtual/abstract 成员时，优先覆写它。
2. 框架注册扩展：角色、设置、资源和池子若有正式注册 API，优先使用注册 API。
3. Harmony 补丁：只有目标没有稳定原生入口，或需要观察/修正引擎流程时才使用。

不要因为类名看起来像入口，就默认它是可覆写的；先确认成员是否 virtual、调用方是否真的经过它，以及补丁是否已执行。

## 异步方法的规则

- 原版返回 Task 的方法，补丁必须保留并等待原任务；涉及 async 的 Postfix 要核对 Harmony 对 ref Task 的要求。
- 方法返回不一定等于卡牌、伤害、动画或 UI 已完成。完成判据应放在实际结算完成后的钩子，或者等待明确的完成任务。
- 去重标志要覆盖完整生命周期：开始、等待、成功、失败、取消都能释放；不能只在“谁先完成”时清理。
- 预览和实打共享一个 Hook 时，要用明确的渲染/提交状态区分，不能靠临时改字段猜测。

## 卡牌、牌堆和目标

- 牌在处理过程中暂时不属于某个牌堆时，用当前版本真实的 Pile == null 等状态表达，不要虚构塔1 的中间牌堆。
- AutoPlay、输入确认、动画开始都不能自动当作结算完成；需要按调用链确认卡牌真正离开处理流程的时点。
- “本回合打出的牌”应优先使用引擎的历史记录或正式钩子，不要拿当前 PlayPile 这种相似但不同的集合替代。
- 随机攻击不要提前保存一个具体目标；使用原版动态目标构造器，让目标在正确的执行时点重新求值。
- 随机发牌不能只按角色和卡牌类型过滤；应复用原版资格规则，包括可生成、可加入、稀有度、池子和当前状态等门槛。
- 选择、随机、指定三种从弃牌堆取牌操作是不同语义，必须阅读对应 Action/Command 的实现。

## 注册与可变模型

- 模型发现、进入卡池、运行时按 ID 获取是三件事，不能混为“类存在就能用”。
- 需要加入池子的对象要在池子冻结前登记；遗物、卡牌、药水和角色的池规则要分别确认。
- 规范模型和运行时可变模型通常不是同一个对象；施加能力、改层数或执行效果前按 API 创建可变实例。
- 一个类型/ID 只登记一次。自检应复用已登记实例，不能为了测试再次 new 出同类型对象造成重复注册。
- 引擎和框架同时提供同名注册入口时，优先选择框架的正式入口，不要补丁设置界面或内部数组。

## 伤害和数值

不要凭“乘区”直觉推导伤害。当前版本要从真实的 ModifyDamage/伤害命令调用链确认：附加值、乘法、上限、格挡、掉血和后续钩子的顺序可能不同。验证时记录每一阶段输入与输出，并用最小场景区分 powered attack、unpowered damage、可被格挡和不可被格挡。

塔1 的 DamageType.NORMAL、攻击类别或“敏捷”等名称，不能直接当成塔2 的同名概念。要写出映射表，并保留反编译证据和实机结果。

## 取证记录格式

每次 API 结论至少记录：目标类型/成员、实际调用点、输入状态、输出状态、适用版本、验证方式和未覆盖情况。若只看到了声明，没有看到调用点，结论只能写成待验证，不得写成硬规则。

## 随机、回放与联机一致性

涉及随机目标、随机选牌、随机奖励或随机资源时，优先使用游戏提供的 RNG / 随机上下文，不要直接使用 System.Random 或静态全局随机源。否则单机看似正常，回放、联机或需要复现的 bug 可能出现不同结果。

实现时还要区分“何时抽随机值”和“何时执行结果”：不要在预览、构造对象或提前缓存阶段过早消耗随机值；在引擎规定的结算时点取值，并记录足够的上下文（来源、候选集合、选择结果）以便复现。
