# 图片、动画、UI 与音频的验收方法

美术资源“看起来差不多”不等于运行时契约正确。验收要同时关注资源内容、路径、尺寸、节点类型、事件路由和最终显示位置。

## 图片与描边

先确认用户说的是运行时图标、百科缩略图、百科详情图、卡面图、黑色描边还是白色描边。相同对象的这些显示层可能完全独立。统一描边时，保留独立部件和透明间隙，避免用最大连通块清理掉瓶盖、剑柄或装饰物。

## 动画交付

交付前检查骨架、贴图、图集、动画名、节点类型、锚点、透明边界和必要的资源引用。状态机声明了不存在的动画名时，可能整条状态机静默不工作，因此必须把“声明的每个名字都存在”作为硬断言。

视觉 cue 使用全量基准状态：颜色、透明度、缩放、偏移、发光和粒子开关都显式写出。不能依赖前一个 cue 恰好留下的状态。

## UI 状态和预览

输入确认、预览、提交、结算是不同状态。若箭头、队列、提示或计数在预览时提前改变，必须设计明确的预览/已提交/已结算状态，防止卡牌离开预览区时来回跳跃。满队列提示应与对应 UI 槽位使用同一套呼吸/闪烁时间基准，预览时提示，提交后清理。

不应拦截交互的覆盖层设置正确的 MouseFilter；否则会产生“点击了别的按钮却触发这个控件”的错觉。

## 音频

先确认播放事件和触发条件，再处理声音文件。音量、锐度或尾音问题可能是混音问题，也可能是事件路由过宽。至少要检查调用事件、触发卡牌/动作和目标对象、采样率/声道/时长/峰值/响度、引擎导入文件和 PCK 条目，以及无关按钮/地图/牌库/其他角色是否会误播。

变体可以通过轻微的音高、起始裁切、尾音或层次差异减少机械重复，但必须保持事件用途一致，并逐个检查可解码、时长、峰值和听感。只有在基础事件路由正确后，才值得继续调音色。
