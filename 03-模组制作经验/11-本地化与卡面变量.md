# 本地化、卡面变量与描述生成

卡面文字通常不是 JSON 原文直接显示，而是“键、模型变量、关键字、升级状态和格式化流程”共同生成的结果。排查文字问题时，必须检查最终显示链。

## 键名先按对象类型确认

不同对象的键名层级可能不同；卡牌、遗物、能力、药水和角色不能只凭一个对象推断全部规则。先从当前版本原版本地化和运行时构造逻辑确认表名、条目段、实体变体、完整键集合，以及代码是否动态拼接键名。

点号键不一定是冗余或错误，它可能代表实体变体。删除前先查调用方和原版对应项。

## 关键字和升级

- 引擎可能自动把关键字文本前置或后置到描述中；本地化里再次手写会造成重复。
- 升级后的数值、关键字和描述条件，优先在模型的升级生命周期里修改；不要把未被引擎读取的升级键当作唯一来源。
- 只有确实由引擎支持的条件格式才可写进描述。若一个效果需要真实运行时变化，不能只换一句文字。
- 验收时同时查看普通、升级、预览和悬停提示四种显示位置，因为它们可能走不同格式化路径。

## DynamicVar 约定

每一个描述占位符都必须有对应的规范变量，且变量名称、类型、大小写和升级行为一致。常见失败包括变量未声明、变量名后缀错误、数值类型不匹配、升级修改了临时值、同一个能量或数字占位符被声明两次。

静态检查只能证明键和变量名字相符，还要在运行期生成最终文本，检查普通值、升级值和边界值。

## 读取和断言

- 区分调试表示、原始文本和格式化文本；直接 ToString 不能作为文本断言。
- 缺键先用支持的存在性 API 检查，再决定是键名错误还是格式化错误。
- 文本断言要读实际卡面使用的牌堆/状态上下文，不要只读一个默认对象。
- 需要做自检时，使用稳定的文本指纹或关键片段，但同时排除合法的动态数值；指纹只能证明当前期望版本，不代表永久兼容。

## 资源闭环

任何本地化 JSON 的修改都必须重新导入、重新打包并在运行时检查最终句子。只编译 DLL、只复制 JSON 或使用 SkipPack 得到的“成功”，都不足以证明游戏使用了新文本。

## 富文本和空白

只使用已在当前版本原版资源或解析器中确认的标签。对中文空格、不可见字符和换行要做可视化/代码点检查；普通 Contains 可能被零宽字符或 Word Joiner 误导。清理时保留有语义的富文本标记，并在游戏内复核排版。
