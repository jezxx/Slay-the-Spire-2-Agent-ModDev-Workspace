# 队列、计数与状态投影

连续技、连击、蓄力、待处理效果和队列式 UI 都适用同一条原则：队列或计数模型是事实源，状态栏 Power、卡面预览和动画只是投影。

## 事实源和投影

- 只允许一个组件负责新增、移除、截断、重排和结算队列。
- Power、状态栏图标、卡面数字、悬停提示和预览箭头从事实源同步，不要让每个显示层各自维护一份计数。
- 任何消耗一层、回退一项或重演一项的效果，都先操作事实源，再统一刷新投影。
- 投影刷新失败不能反向修改事实源；日志要区分“逻辑状态正确、显示失败”和“逻辑本身错误”。

## 多入口与幂等

同一个用户动作可能经过主出牌入口、附魔入口、回放入口或兜底 Hook。应为一次逻辑事件设计明确的认领键或生命周期标志：

- 计数入口和补偿入口不能把同一动作计两次；
- 不应计数的动作仍可能需要完成回转、清理或动画收尾；
- 去重标志覆盖开始、等待、完成、异常和取消；
- 不要用“哪个异步入口先完成就释放”作为唯一规则。

自检必须用正向日志证明每个入口是否命中、是否跳过以及跳过原因。

## 预览、提交与结算

输入确认不等于效果结算完成。队列式 UI 至少区分：

1. 预览：显示如果现在执行会得到的结果；
2. 已提交：卡牌离开输入区，但实际异步效果仍在处理；
3. 已结算：事实源完成更新，投影接受新状态；
4. 清理：取消、失败或场景切换时移除临时状态。

箭头、队列、计数和提示不能在这几个阶段之间来回读取不同来源，否则会出现“预测结果 → 旧真实值 → 新真实值”的跳跃。满队列提示和槽位提示如果表达同一状态，应共享同一条呼吸/闪烁曲线和时间参数。

## 条件和副作用

资格判断、门槛判断和预览计算应是纯读取。不要在 IsPlayable、CanEnchant、预览 Hook 或条件查询中顺便消费一次性豁免、修改计数或注册对象。真实出牌开始时读取一次最终条件快照，再由结算流程写入状态。

## 验收

至少验证：正常新增、连续新增、满队列替换、取消预览、卡牌未打出、异步失败、回放/重演、回合结束清理、场景切换和多目标。每个场景都要同时核对事实源、Power/UI 投影和用户可见动画。
