# 音频处理、路由与变体设计

音频问题经常被误判成“文件不好听”。播放事件挂错、全局 UI 事件过宽、导入缓存旧、响度不匹配，都可能造成同样的听感。先修路由，再调声音。

## 先确认事件

为每个声音记录：触发动作、调用入口、目标对象、事件路径、角色/卡牌条件、停止条件和是否允许叠加。用无关按钮、地图、牌库、其他角色和不同战斗场景做反向测试，确认没有误播。

如果游戏使用事件系统而目标事件不存在，不能假设把文件放进 res:// 就会自动播放。需要按当前框架提供的虚拟事件、资源路径映射或等价扩展点接入，并记录版本限制。

## 以参考音频为基准

处理前记录参考音频与目标音频的采样率、声道、时长、峰值、响度、瞬态和尾音。比较时至少看：

- 峰值是否过大，避免中攻击整体压过参考；
- 高频/高能量比例是否造成刺耳或“钝器感”；
- 起始瞬态是否清晰，尾音是否拖沓；
- 不同等级的声音是否有层次，而不是只有音量变化。

听感调整应保留可回退的中间产物，不要覆盖唯一源文件。

## 变体设计

同一事件需要减少机械重复时，可以离线生成少量轻微变体：微小音高变化、起始裁切、尾音长度、层次混入或轻微响度差异。变体必须保持同一用途，不得把中攻击变成重攻击，也不能靠大幅随机化掩盖路由问题。

音高变化若要保持时长，使用能保持时长的音高处理；不要无条件再叠加 atempo。每个变体都要单独检查可解码、时长、峰值、响度和首尾点击声。

## 导入链与脚本

许多 Godot 音频资源至少涉及源文件、导入描述和 imported 缓存三层；导出过滤器必须递归包含目标目录。改音频后清理限定范围的旧导入物，重新导入、打包并检查 PCK 条目。

Windows 下调用 ffmpeg 等外部程序时：

- 通过参数数组传递参数，不拼接未经转义的整条命令；
- 处理包含冒号、竖线和空格的滤镜参数时，先确认 PowerShell 和 ffmpeg 各自的转义层；
- 记录 stdout、stderr 和退出码；
- 若工具依赖 PATH，兼顾用户 PATH、系统 PATH 和后台进程的环境差异。

## 完成判据

基础事件在正确操作下只播放一次；无关操作不播放；所有变体都能解码；音量和瞬态与参考层级相容；PCK 含本次文件；真实游戏中从触发到停止的时序正确。只有满足这些条件后，才算音频处理完成。

## 音频处理工具的迁移边界

音频工具可以公共化为“事件路由、参考音频、基础版、变体版、响度/瞬态/频谱/尾音验收”的流程，但不能公开私人原始音频和审美参数。生成变体时保留随机种子或参数记录，避免只凭文件能播放就判定完成。
