# 依赖、注册与架构边界

模组工程通常同时面对游戏原生 API、第三方框架和自己的工具。公共经验只给判断原则，不把某个项目的依赖版本或私有路径当成通用前提。

## 依赖边界

- 编译期引用、运行期依赖、资源导出依赖和开发工具依赖是四类不同事情。
- 环境预检要分别报告它们；缺少 Python 不应伪装成 C# 代码错误，缺少 Godot 也不应诱导 Agent 改业务代码。
- 依赖框架有正式部署或注册步骤时，优先使用该步骤；不要为了让编译通过而关闭部署。
- 版本升级后先重新导出 API/程序集索引，再处理兼容性；旧版本反编译资料只能作为线索。

## 注册边界

- “类能被反射发现”“对象进入池子”“能按 ID 获取”“本地化存在”“资源可加载”是不同检查。
- 角色、卡牌、遗物、药水、能力和附魔的注册/池规则不要互相套用。
- 一个模型类型或 ID 只能注册一次；测试代码应复用已注册对象，避免自检制造重复注册。
- 注册 ID 和本地化前缀以运行时日志、原版资源和当前版本 API 为准，不要只根据类名或 ToString 猜。

## 补丁边界

Harmony 补丁必须有明确目的、目标成员和撤销/兼容策略。入口中显式调用 PatchAll，并用 PatchInfo 或正向日志证明补丁真正挂载。若原生生命周期已经能满足需求，优先使用原生入口，减少补丁顺序和版本变化带来的风险。

多个补丁修改同一个属性或流程时，使用明确优先级或合并为单一协调入口。不要依赖同优先级 Postfix 的偶然顺序。

## 设置与用户开关

设置、开关、状态栏角标等功能，优先走框架提供的注册、持久化和显示扩展点。不要直接改设置页面内部节点，除非当前版本没有稳定扩展点，并且已经记录节点定位和版本限制。
