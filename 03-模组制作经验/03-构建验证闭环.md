# 构建、打包、部署和验证

编译成功只说明代码能够生成程序集，不说明模组已经加载，也不说明资源和本地化已经生效。

## 基本闭环

1. 编译源码。
2. 生成资源包。
3. 部署 DLL、清单和 PCK。
4. 通过 Steam 启动游戏。
5. 等待真实模组初始化日志。
6. 读取正向自检和错误日志。
7. 按用户的复现步骤验证行为。

## 资源修改的特殊要求

修改图片、音频、场景或本地化后，必须重新导入和打包。只复制散装文件或只编译 DLL，不能证明资源已经进入游戏。

## 日志原则

“补丁已挂载”“命令已返回”“自检没有报错”都不是行为成功的充分证据。关键自检必须有正向结果，并且要覆盖实际调用或实际资源读取。

## 公开工作流脚本的已验证坑

- NuGet 可能因为用户临时目录中的旧 NuGetScratch 锁文件失败，错误表面上容易被误认为 SDK 或工程引用损坏。公开构建脚本把 TEMP 和 TMP 指向工作区内的 .build-tmp，再判断真正的编译结果。
- 构建脚本不能假设 bin\Release\net9.0 一定是唯一产物位置，应优先通过 MSBuild 的 TargetPath 定位，再用默认路径兜底。
- 只看到 dotnet build 返回成功还不够。至少要检查 DLL 存在、DLL 不早于最近源码修改，并在需要时用 -Deploy false 将编译和部署分开验证。
- 公开脚本不能写死作者的游戏盘符、私人模组名、RitsuLib 布局或个人工具目录。所有游戏目录和数据目录都必须由用户参数提供，默认值只能指向公开包内部的资料目录。
- 做整包自动检查时，要区分工作区元数据与原始游戏资源：manifest、workspace.json、资料清单等应严格解析；PCK 提取出的本地化文件可能只是引擎资源语法，严格 JSON 解析失败本身不代表资料损坏。
