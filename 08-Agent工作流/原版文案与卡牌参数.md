# 原版文案检索与卡牌参数

> 这份文档规定玩家可见文案应该去哪儿查、按照什么顺序查，以及制作一张卡牌前哪些信息必须先问清楚。
> 它适用于卡牌、Power、遗物、药水、关键字、悬停提示、附魔、负面效果和事件中的机制文案。

## 0. 基本原则

玩家可见文字不能凭印象自创，也不能为了“读起来更顺”擅自润色原版句子。

- 原版存在一字不差的句子：直接复用。
- 原版只存在对应关键字、占位符或句式：沿用原版写法，不改关键字语义。
- 原版完全找不到，或资料和运行时行为冲突：停止实现，向用户说明缺口并给出 2 至 3 个方案；不能自行决定一个“差不多”的写法。
- 中文是玩家最终看到的第一依据；英文用于在中文未命中时定位同一个条目，并对拍机制措辞。
- 文案依据和机制依据分开：本地化文件证明“怎么写”，源码和程序集证明“怎么实现”。

## 1. 唯一优先来源：当前版本本地化提取件

公开工作区按游戏版本保存资料。当前 `0.111.0` 的提取件位于：

```text
02-游戏反编译资料\版本-0.111.0\API索引\pck_extract2\localization\
```

其中有 `zhs` 和 `eng` 两个目录，每个目录目前包含以下表：

| 文件 | 用途 |
|---|---|
| `cards.json` | 卡牌名称、描述和升级相关文字 |
| `powers.json` | Power 名称与描述；许多遗物、药水的效果文字实际落在这里 |
| `relics.json` | 遗物名称与描述 |
| `potions.json` | 药水名称与描述 |
| `card_keywords.json` | 卡牌关键字词条全集，包括名称和描述 |
| `static_hover_tips.json` | 静态术语和悬停提示 |
| `enchantments.json` | 附魔名称与描述 |
| `afflictions.json` | 负面效果名称与描述 |

优先使用 `pck_extract2`。同一版本下还可能存在较早的 `pck_extract`，它的表更少，不能因为旧目录先搜到就改用它。

如果工作区以后加入新的游戏版本，先把路径中的版本号替换为目标版本，并确认该版本确实存在；不能拿旧版本的文案当作当前版本事实。

## 2. 标准检索顺序

每次写玩家可见文案，按下面顺序执行。检索过程通常在内部完成，不需要向用户汇报路径和搜索过程。

### 第 0 站：先查 `card_keywords.json`

`card_keywords.json` 是原版关键字词条的集合。先看它，是为了确认：

- 用户说的词是不是原版关键字；
- 关键字在中文和英文中分别怎样写；
- 关键字是否由引擎自动插入卡牌描述；
- 关键字的正文是否不应该重复手写在卡牌描述里。

当前 `0.111.0` 资料中的关键字包括永恒、虚无、消耗、固有、保留、奇巧、不能被打出等词条。实际制作时仍以目标版本文件内容为准，不要只凭这份举例列表判断。

关键字机制可对照当前版本源码：

```text
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Entities.Cards\CardKeywordExtensions.cs
```

如果要制作的内容本身就是一个关键字，优先直接复用 `card_keywords.json` 中的原文和对应机制，不要把它当成普通描述句重新编写。

### 第 1 站：中英文全目录搜整句或核心片段

先搜用户给出的完整句子；没有命中，再搜能唯一定位语义的短片段。中文和英文都要搜：

```powershell
rg -n "失去生命" "02-游戏反编译资料\版本-0.111.0\API索引\pck_extract2\localization\zhs"
rg -n "lose HP|lose health" "02-游戏反编译资料\版本-0.111.0\API索引\pck_extract2\localization\eng"
rg -n "BLOCK_NEXT_TURN|BlockNextTurn" "02-游戏反编译资料\版本-0.111.0\API索引\pck_extract2\localization"
```

中文命中时直接使用对应中文条目；只有中文没有命中时，才用英文条目的 key、变量和句式帮助定位。找到完全匹配的原句后照抄，不改标点、颜色标签、占位符、关键字顺序或句末格式。

### 第 2 站：按对象类型查句式，同时查 `powers.json`

第 1 站没有完整命中时，再按正在制作的对象查对应表：

- 做卡牌：`cards.json`
- 做遗物：`relics.json`
- 做药水：`potions.json`
- 做 Power：`powers.json`
- 做悬停提示：`static_hover_tips.json`
- 做附魔：`enchantments.json`
- 做负面效果：`afflictions.json`

无论制作哪种对象，都必须同时查看 `powers.json`。原版效果的显示文字不按照“它是卡牌、遗物还是药水”分家，很多对象只是触发同一个 Power。

如果只命中句子的一半，寻找包含相同效果、触发时机和动态变量的完整句式。颜色标签和动态占位符必须沿用原版格式，例如 `[blue]{BlockNextTurn}[/blue]`，不能只复制自然语言而丢掉引擎变量。

### 第 3 站：彻底找不到时停止

不能找到足够依据时，向用户明确说明：

1. 已经确认找不到的是原句、关键字、变量，还是机制实现；
2. 当前能确认的部分是什么；
3. 需要用户在 2 至 3 个方案中选择什么。

没有用户选择前，不得自创本地化句子、占位符名称或实现方式。

## 3. 同一效果不按卡牌、遗物、药水分家

原版常见的统一结构是：

```text
触发钩子 -> Power 承载状态 -> Cmd/动作发放效果
```

例如遗物“自成型黏土”的“每当你在战斗中失去生命”效果，会使用下回合格挡相关的 Power。`BlockNextTurn` 不是“某种只属于遗物的发放方式”，而是一个真实的 Power 键名；对应源码入口是：

```text
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Models.Powers\BlockNextTurnPower.cs
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Models.Relics\SelfFormingClay.cs
```

施加这个效果的卡牌、遗物或药水可以共用同一个 Power。卡牌、遗物和药水的区别通常在于触发钩子和目标对象，而不是描述模板或 Power 本身。

涉及命令时，对照：

```text
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Commands\PowerCmd.cs
```

因此，遇到“每当失去生命”“下回合获得格挡”“获得某个状态”等描述，不能只搜索正在制作的对象类型；要在全部本地化表、Power 源码和相关触发对象中交叉核对。

## 4. 动态变量、格式化和升级

描述中的 `{Damage}`、`{Block}`、`{Magic}`、`{Energy}`、`{BlockNextTurn}` 等不是普通文字，而是由模型动态变量和格式化流程生成的显示值。

写入本地化前要核对：

- 占位符名称、大小写和类型是否与当前版本 API 一致；
- 基础值和升级值是否使用同一个动态变量实例；
- 变量是否需要 `diff()`、百分比、图标或其它 formatter；
- 升级后是修改数值、修改关键字、修改目标，还是切换另一段描述；
- 引擎是否会自动插入关键字、句号或颜色标签；
- 普通卡面、升级卡面、预览、悬停提示是否经过同一条格式化路径。

当前版本的动态变量源码位于：

```text
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Localization.DynamicVars\
02-游戏反编译资料\版本-0.111.0\反编译源码\MegaCrit.Sts2.Core.Localization.Formatters\
```

只在 JSON 中看到占位符，不能证明运行时一定会正确显示；需要同时对照模型代码和最终运行文本。

## 5. 结构化查询资料

需要确认卡牌的类型、费用、稀有度、目标或本地化对应关系时，优先使用当前版本 API 索引和本地化表；不要依赖人工记忆或只看条目数量。

工作区中可能提供结构化扫描表或查询工具。使用前先确认它的版本和生成状态；如果没有对应表，就回到：

1. `pck_extract2\localization\zhs` / `eng`；
2. 当前版本反编译源码；
3. `02-游戏反编译资料\版本-<版本>\API索引\` 下的签名、枚举和索引。

结构化表只能帮助定位，不能单独证明运行时行为。最终仍要对拍真实模型、调用点、打包内容和游戏内显示。

## 6. 写一张卡之前必须问齐的参数

以下信息缺哪项就问哪项；用户已经明确说过的项目不要重复询问。不能因为“普通卡一般都是这样”就替用户决定。

| 参数 | 必须确认的内容 |
|---|---|
| 归属 | 哪个模组、哪个角色、是否属于特定卡池 |
| 卡名 | 中文名、英文名或是否需要 Agent 代拟 |
| 费用 | 基础费用、升级后费用、是否 X 费或特殊费用 |
| 类型 | `Attack` / `Skill` / `Power` / `Status` / `Curse` |
| 稀有度 | 基础、特殊、稀有等具体归类 |
| 目标 | 单体、全体、自身、随机、无目标或其它目标规则 |
| 基础效果 | 不升级时完整效果和触发时机 |
| 升级效果 | 升级改变的数值、关键字、目标或额外效果 |
| 关键字 | 消耗、虚无、固有、保留、奇巧等；是否由引擎自动插入 |
| 动态变量 | 伤害、格挡、魔法值、能量、差值、百分比等占位符 |
| 触发范围 | 战斗内/战斗外、自己的回合/任意时机、每回合/每场等 |
| 美术 | 是否需要制作卡面、素材是否已有、正式文件放在哪里 |
| 入池 | 是否自动进卡池、特殊解锁、生成或排除限制 |

描述越简短，越要逐项补齐；描述越完整，越只追问还会改变实现的缺项。所有参数齐全后，仍要先完成本文的文案检索，再进入代码实现。

## 7. 验收

修改玩家可见文案后，最低要检查：

- 本地化键存在且没有重复或拼写错误；
- 占位符名称、大小写和类型与模型一致；
- 关键字没有被手写重复，也没有因自动插入而遗漏；
- 普通版和升级版的最终文本都能生成；
- 若修改会进入 PCK，重新导入、打包并检查 PCK 条目；
- 运行时确认游戏实际读取了新 PCK，而不是旧缓存；
- 画面排版、颜色、换行和实际手感留给用户进行实机确认。

只编译 DLL、只复制 JSON、只看到文件存在，均不足以证明新文案已经在游戏中生效。

## 8. 维护边界

- 文档中的路径都相对于公开工作区根目录，不写个人电脑盘符。
- 版本升级时复制到新的版本目录并重新核对，不覆盖旧版本资料。
- 新发现先记录在对应项目或待整理经验中；确认具有跨项目价值后，再整理到公共经验文档。
- 本文只规定检索和参数确认，不替代当前版本源码、构建脚本和目标模组的专属约定。
