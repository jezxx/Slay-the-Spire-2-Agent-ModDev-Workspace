# 私人工具迁移审计与使用方法

更新时间：2026-10-04

本文件记录一类常见情况：私人工作区里可能有很多已经验证过的脚本，但脚本本身绑定了某个模组的类名、资源目录、运行日志格式或用户审美，不能直接复制到公共工作区。此时要把“工具代码”和“工具背后的工作方法”分开判断。

## 结论总表

| 工具类别 | 是否适合公共化 | 公共区处理方式 | 不能直接复制的原因 |
|---|---|---|---|
| 卡牌字段、规格、升级提取 | 是 | 已迁入通用脚本 | 只读取塔1源码中的机械字段，输入和输出可以参数化 |
| 卡牌本地化生成与空格检查 | 是 | 已迁入通用脚本 | 占位符转换可以通用；项目关键字必须显式传入 |
| T1/T2 卡牌契约断言 | 是 | 已迁入显式输入版本 | 比较框架通用，具体映射和运行时契约由用户提供 |
| PCK 动态资源验证 | 是 | 已改为资源清单版本 | 原脚本的资源路径集合属于项目层，验证机制本身通用 |
| 事件、药水、卡池契约断言 | 方法是，原脚本否 | 保留双向集合对拍、运行时事实和 allowlist 方法 | 日志行格式、对象映射和资格规则绑定具体项目 |
| 卡牌文本差异、逐卡审计表 | 方法是，原脚本否 | 保留“规范化后比较”和“逐对象审计表”方法 | T1/T2 本地化键、运行时日志和项目映射不同 |
| 角色、药水、附魔和具体角色图像处理 | 方法是，原脚本否 | 写入图像验收和预览流程 | 输入尺寸、素材构图、颜色和审美参数不是公共规则 |
| 通用遗物图标描边与精确 RGB 替换 | 是 | 已迁入公共脚本 | 输入输出和参数可显式传入，不依赖项目资源 |
| 角色动画、VFX 场景生成 | 方法是，原脚本否 | 写入资源契约、场景序列化和指纹验收 | 节点名、动画名、资源路径和 shader 参数依赖项目 |
| 音频提取与变体处理 | 方法是，原脚本否 | 写入音频路由、响度、变体和验收方法 | 原始音频、参考音效和用户审美不能进入公共层 |
| 具体模组资源转换器 | 否 | 只保留路径契约、映射表和报告方法 | 转换器通常同时假设某个角色、目录结构和素材集合 |

## 公共化时应保留的结构

### 1. 输入契约

先写清楚工具需要什么输入：源码目录、JSON、CSV、日志、PCK、图片、音频或 Godot 工具路径。不要让工具通过作者电脑的默认盘符猜输入。

### 2. 输出契约

输出应明确区分：机器可读报告、用户预览文件、实际写入的项目资源和最终部署产物。报告文件应记录输入版本、生成时间、处理数量、失败数量和输出路径。

### 3. 预览和应用分离

会改写用户文件的工具应默认只报告或写入独立输出目录。用户确认结果后再通过显式参数应用。图像、音频、文本和本地化都遵循同一规则。

### 4. 运行时证据

静态检查只能证明文件存在或格式可读。资源类工具至少要继续验证：

1. 文件进入了正确的 PCK 或部署目录。
2. 引擎用真实路径能加载它。
3. 依赖资源也存在。
4. 实际对象能够实例化或显示。
5. 无关对象没有被误改或误触发。

### 5. 失败输入

公共工具必须对缺失目录、空清单、错误扩展名、重复映射、编码错误和不存在的资源路径给出非零退出码或明确警告。不能把“没有处理任何对象”当作成功。

## 各类私人工具的方法提炼

### 契约断言工具

通用做法是让模组运行时只负责打印事实，让外部脚本负责比较和判定。例如运行时输出对象 ID、基础字段、升级字段、池归属或本地化键，脚本再做：

- 期望集合与实际集合的双向比较。
- 基础状态与升级状态的分开比较。
- 可接受差异使用带理由的 allowlist。
- 缺失、未使用和字段不一致分别统计。
- 退出码反映真实失败数量。

这套方法可用于卡牌、遗物、药水、附魔、事件和卡池，但不能把某个项目的日志前缀直接当成公共协议。

### 文本差异和逐对象审计

塔1 到塔2 的文本比较不能直接比较原字符串。应先去掉颜色标签、引擎自动插入的关键字和等价占位符，再把运行时数值代入，最后比较语义骨架。对于无法自动判断的卡牌，应生成一张一对象一文件的审计表，保留原文、目标文、运行时值、人工结论和差异影响。

### 图像处理工具

通用流程是：高分辨率源图保留在输入区，处理结果写入独立输出区；先确认 alpha、尺寸、主体包围盒和透明边缘，再做缩放、描边、去底或颜色处理；最后用缩略图和实际游戏尺寸分别预览。不要把某一张图的坐标、颜色或边缘半径写成所有项目的硬规则。

### 音频处理工具

先确认事件路由，再处理声音本身。处理链应保留原始音频、参考音频、基础版和变体版，分别检查响度、瞬态、频谱重点、尾音和实际触发对象。仅凭峰值或文件能播放，不能判断音效已经正确；还要确认不相关的卡牌或 UI 不会误播。

### 动画和 VFX 工具

先建立资源契约：运行时版本、骨架/场景格式、节点结构、动画名、贴图依赖、材质参数和挂载点。复杂场景由引擎序列化，生成后做无头加载、节点数量、动画库、自动播放和关键参数检查。原版资源复制时保留字段指纹，只有确实需要变化的字段才改。

### PCK 和资源映射工具

资源映射应从对象 ID 出发，经过引擎真实的路径变换，再对拍磁盘文件、PCK 条目和运行时加载结果。路径清单必须由当前项目生成，不能把某个模组的所有资源路径写进公共验证器。预先存在的原版资源应单独标记，不能把它当成模组成功提供资源的证据。

## 私人工具的本地使用顺序

即使工具不进入公共目录，Agent 仍可按下面顺序使用它们：

1. 先读取脚本参数、输入输出和是否会覆盖文件。
2. 用项目当前版本的源码、程序集和运行日志生成报告。
3. 先执行报告模式或 dry-run，不直接覆盖资源。
4. 检查报告中的数量、缺失项、重复项和路径。
5. 用户确认预览后，再写入项目目录。
6. 重新构建、打包并用运行时自检验证。
7. 将可跨项目的失败原因提炼到公共经验，将具体映射、资源和用户选择留在项目档案。

## 本轮审计结论

事件、药水、卡池断言工具没有直接迁入，但它们的“双向集合对拍、运行时事实、allowlist 和退出码”已经转为公共方法。图像、音频、动画、VFX 和具体资源转换工具也没有复制私有素材或项目参数；可复用的处理顺序、验收证据和失败边界已经写入公共经验区。
